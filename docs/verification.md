# 验证范围与已知限制

本文说明应运行的检查、各类证据能证明什么，以及仍开放的限制。命令和依赖见[开发指南](development.md#检查入口)，桌面操作见[模拟器指南](simulator.md)，E2E 场景见[覆盖矩阵](design/simulator-e2e-coverage.md)。硬件资料入口见 [StopWatch 开发资源](verification/stopwatch-c152-dev-resources.html)。

当前实现为全国图鉴 1～649、320 条进化边、五个世代地区、中英文界面、schema8、ruleVersion 3。“覆盖”仅描述测试范围，是否通过以本轮命令和产物为准。

## 每次任务的 E2E 验收要求

默认按影响范围选择专项检查和定向 E2E，不以“改了代码／测试／配置”“新增功能”或“准备提交 PR”作为全量触发条件。

| 改动 | 默认验收 |
| --- | --- |
| 文档、注释、说明截图等非行为改动 | 内容、链接和格式；不跑 E2E |
| 局部页面、绘制或动画 | 对应渲染套件并读图；交互变化再跑相关 `--case` |
| 单个玩法／输入／保存流程修复或新增功能 | 对应主机测试及受影响的 E2E 场景，覆盖失败与恢复分支 |
| 单场景测试、断言或截图基准 | 跑该场景；共享辅助函数再跑所有使用它的场景 |
| 局部构建配置、素材或生成器 | 相应构建／生成校验；影响运行时再补相关场景 |

**只有以下情况要求全量：**

1. 改变跨多个用户流程的共享状态机、事务提交／恢复语义、全局输入或时钟调度；已有定向场景不能覆盖其交叉影响。
2. 改变存档格式、迁移、CRC／语义校验或双槽存储协议，可能影响所有旧档或恢复路径。
3. 改变全局 E2E runner、场景注册／隔离、公共启动／事件注入，或确实影响全部模拟场景的依赖与环境配置。只更新 runner 中某个场景的截图基准不属于此项。
4. 用户明确要求完整回归，或已约定的发布验收明确要求全量。

全量前说明命中的条件及定向检查不足之处；影响范围不清时先查调用关系和覆盖矩阵，不以“保险起见”默认全量。满足条件后由主 agent 汇总改动，执行一次：

```bash
rtk proxy mise run test-simulator-e2e
```

- **新功能新增覆盖**：在 [test/simulator](../test/simulator) 新增场景或在已有场景中新增该功能的操作链与断言，并接入 [runner](../scripts/run_simulator_e2e.py) 的默认全量运行。仅运行已有测试不算为新功能补测；同步更新[覆盖矩阵](design/simulator-e2e-coverage.md)。
- **验证用户可观察的结果**：操作通过真实 SDL 输入进入 Runtime，断言页面与业务结果；涉及存档时验证真实文件和新进程恢复，涉及失败重试时验证不重复结算。UI 改动还须保留并读取真实渲染截图。仅硬件可验证的部分另列设备验收，不能由模拟器通过代替。
- **迭代使用定向检查**：按改动范围运行专项检查，必要时用 `--case` 或 `--suite core` 验证相关路径。不要每改一个文件、完成一个小步骤就运行全量 E2E。
- **全量统一协调**：只有命中上述条件时才安排全量，由主 agent 或指定的一个验收 agent 执行；子 agent 默认只做职责范围内的定向验证。未命中条件时，定向 E2E 可以作为本次交付验收；`--build-only` 不证明行为通过，`--suite core` 也不是全量。
- **有原因才重跑**：失败先排障并定向复测；修复后重新评估上述条件，局部修复可用定向结果关闭对应失败，记录此前全量中未受影响的结果，不把组合证据写成“最终全量通过”。后续改动只重验受影响范围，不因提交、文档或交接重跑；纯文档等非行为改动也不中断正在运行的验收。
- **以本轮证据报告结果**：使用新的验收目录，记录命令、退出状态、通过／失败场景和证据路径。测试失败、依赖缺失或环境阻塞时，明确报告未完成验收；未运行不能记为通过，也不能删除、跳过失败场景来满足交付条件。

仍须完成[相应专项检查](development.md#检查入口)、固件构建和必要的设备验收；纯文档不重建固件。下述 CI 自动触发不构成本地重复验收要求。

[GitHub Actions](../.github/workflows/simulator-e2e.yml) 对所有 PR、`main` 推送和手动运行执行同一全量入口，不设置路径过滤。Ubuntu + Xvfb 的结果与截图随每次 run 上传，保留 7 天；具体准备步骤见[开发指南](development.md#github-actions)。是否通过以对应提交的 Actions 结果为准。

`test` 的缓存回归用 zlib 调用计数检查双角色交替绘制，只证明避免重复解压，不测量设备帧率。解压缓存最多保留两个来源，各槽复用其已分配容量；ESP32 使用 PSRAM，最坏占用取决于浏览过的素材大小，仍须测量设备动态内存。

历史布局与来源规则仍须按对应版本检查，不能把旧 122 条进化边、251 种素材的通过记录当作当前目录的验收。主机 ABI 的 `sizeof`、编码缓冲容量和构建静态 RAM 也不能代替目标设备的动态内存测量。

## 测试模式的验证边界

[设备内测试模式](usage-test-mode.md)使用独立目录与模式标记。存储回归通过 LittleFS/VFS 替身比较正式槽字节，覆盖快照、空档、RAM-only、重启恢复、标记删除失败、清理失败和写前／写后／加载故障。玩法回归检查模拟时间、IMU／RTC 隔离与手动步数触发遭遇；退出加载使用 `begin(false)`，不提交正式档启动记录。进入前正常保存仍可能更新正式档，比较基线应取保存完成之后。

`test_test_mode_render` 使用真实 Runtime、Button_Class 和 M5GFX，检查顶部长按、来源确认、控制台分页、四种固定场景、步数、模拟校时、故障选择、重置和退出。模式宿主与存储是替身，不执行 `main.cpp` 的完整设备切换链。

以下边界仍开放：

- 没有测试档导入／导出、任意账户编辑、设备内软重启、损坏字节或双槽冲突注入入口；诊断页不展示 CRC、当前活动槽、重试次数或动态内存。
- “读取失败”只影响后续加载；设备重启会清除故障开关。主机重建 Runtime 的测试不能证明设备内存在一键复现路径。
- 大批步数注入遇保存失败后的精确回放缺少端到端覆盖。分批限制在 Engine 队列容量内不等于已证明全部步数会恢复。
- 桌面模拟器未接入设备测试控制台的存储切换；E2E 的练习／预览隔离不替代设备测试模式验收。

## 已知失败与限制

2026-10-31 模拟器集成时记录的两项渲染失败已复现并修正测试，两套定向回归通过，未修改固件行为：

- `test_battle_render`：旧闪环断言在 Runtime 的 40ms 绘制间隔内读取上一帧。现在按节拍选取剩余 80～170ms 的白色闪烁时段，确认允许新帧绘制后，核对对手周围的提示圈为白色。（提示圈改为圈住角色后，断言随之从屏幕外圈改为角色周围。）
- `test_test_mode_render`：菜单辅助函数最多发出三次侧键输入，无法在五项菜单从第 2 项绕回第 1 项。现在先检查目标有效，再以实际菜单项数限制移动次数；保留到达目标和确认后的行为断言。

上述定向结果不能代替本轮全量渲染与 E2E。历史设计稿检查仍有问题：素材解析要求 1～251 与旧格式，实跑在 `setUpClass` 失败，尚未执行断言；另有画廊 26 页与固件 36 页的静态覆盖缺口，见[设计稿维护](design/ui-scene-redesign-implementation.md)。

其他限制：

- 首捕卡与最近捕捉详情中，部分物种的角色阴影压在“地区 · 累计捕捉 N 次”一行文字上；该问题早于五地区改动，尚未修正。
- “资源与数据”页只按 `clock.trusted` 选择“今日／上次记录”，尚未像首页那样区分不完整日桶；部分记录可能被显示为普通“今日”数值。
- RTC 待确认标记清除到最终确认之间仍存在非原子窗口。主机故障注入不能证明实际备电保持或物理断电安全。
- 没有首次 LittleFS 格式化入口。挂载失败保留数据并限制玩法，不能自动格式化来消除错误。
- 本地验证使用 macOS；Ubuntu X11/Xvfb 的全量 E2E 以对应提交的 Actions 结果为准，Linux 真实桌面人工操作尚未验收。模拟器使用 POSIX 文件锁，不支持原生 Windows。端口自动探测仅支持 macOS，多个设备须显式指定端口。
- SDL 队列输入不证明原生 OS 键鼠注入；已有 macOS 检查记录未取得辅助功能和事件投递权限，原生输入尚未验收。
- Runtime/M5GFX/SDL 截图、像素比较与人工读图分别承担不同检查。关键截图抽查不代表全部图片已逐张审阅，Pillow 设计稿不能替代真实渲染证据。

## 设备观察与待验事项

历史设备观察及本地证据索引见[设备观察记录](device-observations.md)，适用范围仅为当时固件。

仍需设备验证：振动在实机上能否感觉到——2026-11-02 实机对战判定振动和原有投球振动均未感觉到，固件以强度 70 振 10～55 毫秒，官方示例每档 500 毫秒，马达本身未实测（见[设备观察记录](device-observations.md)）；在此之后再核对对战振动的手感与可辨识度，及走路判定门限（最近 2 秒有步数时不振动）在实际边走边战时是否既不漏步又不误停振动；四种携带方式的计步误差、真实走路达到 200–500 步目标并完成捕获与保存的全过程、其余按键／触摸场景、伙伴列表／战斗／投球页以外的物理 466×466 圆屏边缘、五个地区场景在实体 AMOLED 上的色带与观感、动画与唤醒时延、跨日关机 RTC 保持、真实失时、满盘与断电恢复、动态堆峰值、完整任务栈、采样间隔和功耗。关机 LDO 保持同时给 RTC 与 IMU 供电，续航代价尚未测量。

## 生成和保留本轮证据

按[开发指南](development.md#检查入口)准备依赖。E2E 和基础模拟器默认创建 `.pio/verification/` 下的新时间戳目录；`MYM5_VERIFICATION_DIR` 可指定尚不存在的目录。渲染、玩法、计步、RTC、校时和存储任务也支持该变量，应为每轮选择独立路径，避免覆盖。

E2E 根目录的 `manifest.json` 记录源码、依赖和可执行文件哈希及环境，`result.json` 汇总场景结果；每个启动阶段保留事件、业务快照、真实存档、截图和进程退出码。三种强杀场景的预期退出码为 SIGKILL（`-9`），必须连同新进程恢复断言判断，不能单看非零退出码。字段说明见[E2E 证据](design/simulator-e2e.md#执行与证据)。

需要命令日志时额外保存标准输出、标准错误与退出状态。重新运行只验证运行时的源码和环境，不能恢复已经清理的历史截图或设备观察。保留现有原始验收数据、Flash 备份及存档，不把它们作为新用户构建的前置条件。

# 测试模式的验证边界

[设备内测试模式](../usage-test-mode.md)使用独立目录与模式标记。`test-storage` 通过 LittleFS/VFS 替身比较正式槽字节，覆盖快照、空档、RAM-only、重建恢复、标记删除／清理失败和写前／写后／加载故障；退出后恢复正式进度。进入前正常保存仍可能更新正式档，比较基线取保存完成之后。

`test-adventure` 中的 `test_test_mode` 仅检查 TestModePlatform 的模拟时间推进、静止样本、模拟校时不改真实 RTC 值，以及退出后恢复真实平台读数。普通 Engine 步数调用不是测试控制台注入证据，也不代表完成设备模式切换。

`test_test_mode_render` 经真实 Runtime／Button_Class／M5GFX 检查设置页／错误页顶部长按、来源确认、分页、故障选择、诊断、空档重置及退出失败重试；通过控制台选择“临近遭遇”场景，再按“+1 步”实际触发遭遇，并检查模拟校时、测试标识和正式槽字节隔离。它不再逐一验证四种场景种子。模式宿主与存储使用替身，由测试处理请求并重建 Runtime，未执行 `main.cpp` 完整设备切换链。

以下边界仍开放：

- 没有测试档导入／导出、任意账户编辑、设备内软重启、损坏字节或双槽冲突注入入口；诊断页不展示 CRC、当前活动槽、重试次数或动态内存。
- “读取失败”只影响后续加载；设备重启会清除故障开关。主机重建 Runtime 的测试不能证明设备内存在一键复现路径。
- 大批步数注入遇保存失败后的精确回放缺少端到端覆盖。分批限制在 Engine 队列容量内不等于已证明全部步数会恢复。
- 桌面模拟器未接入设备测试控制台的存储切换；E2E 的练习／预览隔离不替代设备测试模式验收。

检查入口见[开发指南](../development.md#检查入口)，通用验收要求见[验证说明](../verification.md#每次任务的-e2e-验收要求)。

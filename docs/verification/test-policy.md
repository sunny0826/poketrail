# 测试保留标准

测试只保留能验证产品或逻辑假设的检查，以及构建、打包和发布保障。是否保留取决于失败意味着什么，不取决于它叫单元测试、渲染测试还是 E2E。

## 可以保留的假设

- 步数不能凭空增加、重复消费或转移：只有携带者获得培养步，进化从来源扣费，目标使用自己的历史账户。
- 玩家操作必须得到正确结果：一次按下不跨过两次确认，空等和误触不消耗投球次数，练习不能改变正式进度。
- 保存失败不能提前发奖励，重试和重启不能再次结算；损坏、未知版本和挂载失败不能覆盖原存档。
- 旧档升级仍能继续游戏，已有账户、捕捉记录和合法在途遭遇保留。
- 日期未知、回拨或跨日不能制造历史步数；RTC 故障不能把无效时间当成可信日期。
- 界面必须给出玩家决策所需的信息和可用入口，关键文字、长名称和圆屏边缘不能导致无法操作。动画不能改变已提交的玩法结果。
- 发布素材必须来自固定来源，物种、进化规则、像素与原始动画时长满足产品契约；固件、模拟器和 CI 能构建运行。

每条测试应能说明“破坏这个条件后，玩家会遇到什么错误”或“会怎样阻止正确发布”。设置场景、注入故障和防止测试空跑的前置断言可以保留，但不作为独立覆盖成果。

## 删除的检查

- 内部函数调用次数、缓存替换顺序、容器或对象布局、主机 ABI 大小、与用户结果无关的 revision 或 sequence 精确增量。
- 扫描源码字符串、固定函数组织、把实现中的公式再抄一遍求期望值。
- 整屏哈希、固定颜色与装饰像素计数、动画每帧的私有坐标；素材来源一致性不属于此类。
- 同一假设的重复路径：已有真实用户流程覆盖时，不再以多个层级重复验证普通成功路径。低层独立故障和边界仍可保留。
- Pillow 设计稿的页面数、文档字数或源码结构等检查；设计稿不能证明实际 Runtime 产品行为。

对无法说明独立假设的边界项，倾向删除。不得把“保证实现正确”“防止回归”当作保留理由，也不得因本轮失败才把原本有价值的检查归为冗余。

## 后续维护

新测试先写出要保护的假设，再选择最能观察结果的一层。新增功能优先扩展已有用户旅程中的操作与业务断言；不机械增加每个方法的单元测试。与存档有关的用户流程保留真实文件及新进程恢复证据。

构建、固定来源校验、生成物检查和 CI 工作流语法检查按发布用途保留。当前没有独立的 typecheck 任务，C++ 类型检查由实际主机与固件编译承担。

执行范围、原始证据和设备限制见[验证说明](../verification.md)，任务入口见[开发指南](../development.md#检查入口)。
